# Conversational planner and current-app refinement

Updated 1 October 2026. This is an incremental build in `zania-coherent-production`, preserving the substantial pre-existing local changes. The slice is deployed to Zania's dedicated staging Supabase and Vercel projects. Production remains unchanged.

## Product direction

Keep the working wedding and professional workspaces. Add conversation as another way to understand and use their records. Continue refining the connected enquiry → quote → contract → payment → receipt flow alongside couple planning. The user's conversational-planner brief is the target experience, not evidence of existing capabilities.

## Implemented on staging: first read-only capability

- `supabase/functions/_shared/weddingBriefing.ts`: shared authorized summary and deterministic weekly priorities.
- `supabase/functions/wedding-ai-chat/index.ts`: recognizes “How is my/our wedding doing?” and “What should I/we focus on this week?” as strictly read-only requests. Uses the existing verified session, paid-access and rate-limit gates, then returns structured data and a readable answer without an LLM call. No model tokens or usage debit for this deterministic path; existing allowance gates still apply.
- `src/components/AssistantPanel.tsx`: presents the two questions inside the existing Ask Zania panel. Suggestions give way to the answer once the conversation starts.
- `src/hooks/useInlineAssistant.ts`: discards stale replies when the user changes wedding context, including switching away and back.

## Persistent role-based premium conversation

- Couples, planners and vendors now have a durable conversation scoped to their signed-in identity and role audience. A conversation started in `/ai-chat` is restored in the in-workspace Ask Zania panel and survives page navigation and reloads.
- `assistant_conversations` and `assistant_messages` store the history in staging Supabase. Row-level security permits an authenticated user to read only their own records. Conversation writes run inside the existing authenticated Edge Function after its session, role and paid-access checks.
- Every request carries a client request ID. Unique message constraints make retries idempotent so a retry cannot silently duplicate the same user or assistant message.
- The server and client enforce the premium boundary. Couples receive conversational access through the Collaborative entitlement (or an active eligible trial/pass); planners and vendors receive it through their paid professional entitlement. Existing free users see the upgrade path.
- Ask Zania is mounted throughout the authenticated workspace. The compact launcher opens the same durable conversation from the dashboard and other supported pages; `/ai-chat` remains the full-page surface.
- The current staging beta account was extended through 29 October 2026 for verification. This is a staging test entitlement, not a production plan change.

## Intelligence Gateway foundation

- `docs/ZANIA_INTELLIGENCE_GATEWAY_ARCHITECTURE.md` is the repository's architecture reference for this direction. `AGENTS.md` requires Codex to read it for conversational planner, Gateway, MCP and assistant-client work.
- `supabase/functions/_shared/intelligenceGateway.ts` introduces the canonical internal boundary described in the Intelligence Gateway architecture: versioned capability definitions, risk class, actor and client identity, resource scope, confirmation state, trace IDs, structured data, user summary, warnings, next actions and audit ID.
- The enabled registry contains eleven Class A reads: `get_my_weddings`, `get_wedding_summary`, `get_weekly_focus`, `get_budget_summary`, `get_upcoming_payments`, `get_tasks`, `get_guest_summary`, `get_vendor_summary`, `get_timeline_summary`, `get_planner_portfolio_briefing` and `get_vendor_business_briefing`. Screen operations and the assistant's existing broad write-tool list are not registered as Gateway capabilities.
- The first-party web assistant now invokes the same Gateway executor that future MCP or other adapters can call. The executor receives the caller's JWT-scoped database client; it never receives service-role database access.
- Successful calls are recorded in the existing function event ledger with capability/version, risk class, client identity, wedding scope, authorization decision, confirmation state, source coverage and audit ID.
- `supabase/functions/intelligence-gateway-mcp/index.ts` exposes those same services through an official SDK Streamable HTTP adapter. It advertises only bounded read tools, supplies structured results, identifies every tool as read-only/non-destructive/closed-world, and includes the standard authenticated `get_profile` tool for multi-account clients.
- The MCP adapter uses Supabase's OAuth protected-resource and authenticated-user middleware. Every capability still executes through the Gateway with the caller's RLS-scoped client, paid-plan check, active trusted-session check and audit logging. The adapter contains no domain queries except identity and entitlement resolution.

The read capability resolves a wedding through the signed-in couple's active membership or the professional planner's selected client plus active membership. It refuses vendors, admin context, committee context, revoked/invited memberships, ambiguous couple memberships, and unlinked legacy planner clients. No arbitrary wedding ID grants access. Every data query uses the caller's JWT-scoped client and an explicit wedding ID; no service-role reads are used for the summary.

Sources: tasks, wedding budget categories, wedding budget-payment logs, guests and vendor tracker. Each source uses exact counts and stable pagination, with an explicit unavailable state on errors, changing counts, or exceeding 10,000 rows. Only minimal fields are fetched. Guest counts are records, not attendees including plus-ones. Personal budget scopes are excluded.

Priorities: up to three open tasks or selected-vendor payment dates, ordered by date, through today plus six days in Africa/Nairobi. A vendor's quote balance is not described as an invoice instalment due. Unknown quote amounts, missing dates and unconfirmed vendor states remain explicit. All answers link to existing workspace routes.

The deterministic router now recognizes the two broad briefing questions plus explicit task, budget, upcoming-payment, guest, vendor, timeline and accessible-wedding requests. Other questions continue through the existing assistant. Invoice commitments, provider settlements, cross-wedding rankings and automatic notifications are outside this slice.
